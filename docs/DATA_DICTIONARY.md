## 1. Grain — 1 แถวคืออะไร

**1 แถว = 1 รายการสินค้าในออเดอร์ (order line)** ไม่ใช่ 1 ออเดอร์

ออเดอร์ที่ลูกค้าซื้อ 3 สินค้า → 3 แถว ใช้ `order_id` เดียวกัน

> ⚠️ **คอลัมน์ระดับออเดอร์จะซ้ำในทุกแถวของออเดอร์นั้น**
> `total_amount` `shipping_fee` `payment_method` `province` `buyer_username` เป็นค่าของทั้งออเดอร์
> **ห้าม `SUM(total_amount)` ตรง ๆ** จะได้ยอดเกินจริงตามจำนวนสินค้าในออเดอร์
> ต้อง `SUM(DISTINCT)` ระดับออเดอร์ หรือยุบเป็นตารางออเดอร์ก่อน

### ตัวอย่าง

| order_id | sku | quantity | item_price | total_amount |
|---|---|---|---|---|
| 260807ABC | THT2881 | 1 | 120 | **422** |
| 260807ABC | THT2891 | 1 | 140 | **422** |
| 260807ABC | THT28101 | 1 | 162 | **422** |

ยอดออเดอร์นี้คือ 422 บาท ไม่ใช่ 1,266

## 2. คีย์

| ระดับ | คีย์ | หมายเหตุ |
|---|---|---|
| แถว (order line) | `platform` + `order_id` + `sku` | ดูข้อควรระวังด้านล่าง |
| ออเดอร์ | `platform` + `order_id` | |
| ร้าน | `shop_id` | |

> ⚠️ **`order_id` ไม่ unique ข้ามแพลตฟอร์ม** และซ้ำภายในออเดอร์เดียวกันตาม grain
> ต้องมี `platform` (หรือ `shop_id`) ประกอบเสมอ

> ⚠️ **`sku` ว่างได้ประมาณ 3%** ถ้าออเดอร์เดียวมี 2 บรรทัดที่ `sku` ว่างทั้งคู่ คีย์จะชนกัน
> ผลทดสอบกับข้อมูลจริงอยู่ในหัวข้อ 7
> **ข้อเสนอ:** ฝั่งฐานข้อมูลควรใส่ surrogate key (auto-increment) เป็น PK
> แล้วทำ unique index บน `(platform, order_id, sku)` ไว้จับข้อมูลซ้ำตอน import

## 5. ชื่อร้าน — เรื่องที่ต้องระวังเป็นพิเศษ

**ร้านเดียวกันบนคนละแพลตฟอร์มมักตั้งชื่อไม่ตรงกัน** ระบบจึงแปลงเป็น **ชื่อมาตรฐาน** ก่อนส่งออก

|---|---|
| `powerstool` (TikTok) · `Powerstools` (Shopee) | **Powerstools** |
| `Toolspartner` · `TNLTOOLSTORE` (Shopee ทั้งคู่) | **TNLTOOLSTORE** |
| `เฮียเก๋าเครื่องมือช่าง ราคาถูก` (TikTok) · `เฮียเก๋า เครื่องมือช่างราคาถูก` (Shopee) | **เฮียเก๋า เครื่องมือช่างราคาถูก** |
| `100อัน1000อย่าง88` (TikTok) | **100อัน1000อย่าง** |
| `กัปตัน เอกสตีล` (Lazada + Shopee) | **กัปตัน เอกสตีล** |

**ผลที่ตามมาสำหรับการวิเคราะห์**

- `GROUP BY shop_name` = ยอดรวมของ**ร้านจริง** (รวมทุกแพลตฟอร์ม)
- `GROUP BY shop_id` = ยอดแยกราย**หน้าร้านบนแพลตฟอร์ม**
- **1 `shop_name` มีได้หลาย `shop_id`** — ความสัมพันธ์เป็น 1-ต่อ-หลาย

## 7. ผลทดสอบคีย์กับข้อมูลจริง

ทดสอบกับข้อมูลจริง **660,181 แถว** (1 ม.ค. – 31 ก.ค. 2026)

| ผู้สมัครเป็นคีย์ | ค่าไม่ซ้ำ | แถวที่ซ้ำ | ผล |
|---|---:|---:|---|
| `order_id` | 586,711 | 73,470 | ❌ ใช้ไม่ได้ |
| `platform` + `order_id` | 586,711 | 73,470 | ❌ ใช้ไม่ได้ |
| **`platform` + `order_id` + `sku`** | **660,181** | **0** | ✅ **ใช้เป็นคีย์ได้** |
| `shop_id` + `order_id` + `sku` | 660,181 | 0 | ✅ ใช้เป็นคีย์ได้ |

**ข้อกังวลเรื่อง `sku` ว่าง — ทดสอบแล้วไม่เป็นปัญหา**
มี **93,486 แถวที่ `sku` ว่าง** และในกลุ่มนั้น **ไม่มีคีย์ชนกันสักคู่**
(สาเหตุคือออเดอร์ที่ไม่มี SKU มักมีสินค้ารายการเดียว)

> ทดสอบครบทุกแถว ไม่ได้สุ่มตัวอย่าง — สคริปต์อยู่ที่ `scripts/probe_keys.py` รันซ้ำได้

**ข้อเสนอสำหรับ schema**

```sql
CREATE TABLE order_line (
    id              BIGSERIAL PRIMARY KEY,      -- surrogate key
    order_id        VARCHAR(64)  NOT NULL,      -- TEXT เท่านั้น
    platform        VARCHAR(16)  NOT NULL,
    shop_id         VARCHAR(32)  NOT NULL,
    shop_name       VARCHAR(128) NOT NULL,      -- ชื่อมาตรฐาน
    sku             VARCHAR(128),               -- ว่างได้ ~3%
    ...
    UNIQUE (platform, order_id, sku)            -- จับข้อมูลซ้ำตอน import
);

CREATE INDEX idx_created  ON order_line (order_created_at);
CREATE INDEX idx_shop_day ON order_line (shop_id, order_created_at);
```

## 8. ข้อควรรู้เรื่องการอัปเดตข้อมูล

- ระบบดึง **ข้อมูลของเมื่อวาน** ทุกเช้า 08:30 น.
- **สถานะออเดอร์เปลี่ยนได้หลังดึงไปแล้ว** เช่น `SHIPPED` → `DELIVERED` หรือถูกยกเลิกภายหลัง
  ข้อมูลที่ดึงไปแล้วจะ**ไม่ถูกอัปเดตย้อนหลังอัตโนมัติ**
- ถ้าต้องการสถานะล่าสุด ต้องดึงย้อนหลังใหม่ (มีคำสั่ง `backfill`)
- แนะนำให้ฝั่งฐานข้อมูลทำ **upsert ด้วย `(platform, order_id, sku)`** ไม่ใช่ insert อย่างเดียว
  จะได้รองรับการดึงซ้ำเพื่ออัปเดตสถานะโดยไม่เกิดข้อมูลซ้ำ

## 9. คำถามที่ยังเปิดอยู่ — ต้องคุยกันก่อนออกแบบเสร็จ

1. **ต้องการข้อมูลย้อนหลังแค่ไหน** ตอนนี้มี ม.ค.–ก.ค. 2026 (660,181 แถว) พร้อมส่ง
